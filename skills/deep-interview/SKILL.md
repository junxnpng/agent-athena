# Deep interview — 결정과 근거로 요구사항 구체화

먼저 [공통 실행 계약](../shared/PORTABILITY.md)을 읽는다.
OMC의 불확실성 우선 질문과 Matt의 의사결정 의존관계를 함께 사용한다.

## 질문할 것과 직접 확인할 것

기존 대화·사양·관련 코드를 먼저 읽고 목표, 제약, 성공 기준, 기존 시스템 맥락을 짧게 정리한다. 파일에서 확인할 사실은 직접 조사한다. 사용자에게는 선호·우선순위·허용 범위처럼 사람이 결정해야 할 것만 묻는다. 읽지 못한 기존 시스템을 새 프로젝트라고 재분류하지 않는다.

탐색 도구나 접근 가능한 경로가 없어 직접 확인할 수 없다면, 필요한 파일 위치나 관련 발췌를 요청할 수 있다. 확인하지 못한 사실은 미확인으로 남기고 그 사실에 의존하지 않는 질문부터 진행한다.

이미 실행 가능한 요청이면 인터뷰를 강제하지 않고 남은 가정만 표시한다. 사용자가 질문을 생략하라고 하면 합리적인 가정으로 진행할 수 있는 부분과 답이 꼭 필요한 부분을 나눈다.

## 의사결정 의존관계

- 무엇을 정해야 다른 질문에 답할 수 있는지 연결한다. 목표를 모르는 상태에서 구현 세부 선택을 묻지 않는다.
- 기본은 가장 중요한 미해결 사항 **한 가지**를 묻는다. 지금 결정할 수 있는 서로 독립적인 작은 질문은 사용자의 선호에 따라 최대 세 가지까지 묶을 수 있다.
- 질문마다 필요한 이유, 관련 코드·문서 근거, 권장 선택과 주요 절충을 짧게 제시한다. 같은 묶음의 다른 답에 의존하는 질문은 뒤로 미룬다.
- 답을 받으면 사용자 결정·근거 있는 사실·아직 열린 가정을 구분해 반영한다. 답하지 않은 항목을 동의로 처리하지 않는다.

질문이 막히면 전제를 뒤집어 보거나, 가장 작은 유용한 결과를 찾거나, 핵심 명사가 무엇인지 확인한다. 특정 횟수마다 기계적으로 질문 방식을 바꾸지 않는다.

## 충분히 구체화됐는지 판단

목표를 한 문장으로 설명할 수 있고, 범위·비목표가 구별되며, 성공을 관찰 가능한 예로 확인할 수 있어야 한다. 기존 시스템을 바꾸면 근거 경로와 호환 제약도 있어야 한다. 남은 가정은 사용자가 받아들인 것과 답이 필요한 것을 구별한다.

모델의 주관적 판단을 수치 점수나 수학적 검증처럼 제시하지 않는다. 대신 각 차원에서 무엇이 알려졌고 무엇이 막혀 있는지 보여 준다. 사용자가 중단하면 즉시 멈추고 미해결 사항을 남긴다. 대화가 길어져도 답을 대신 결정하지 않는다.

## 결과

정리 문서가 요청되면 [to-spec](../to-spec/SKILL.md)의 공통 형식으로 목표·제약·성공 기준·결정 근거·미해결 질문을 저장한다. 인터뷰만 요청받았다면 구현을 시작하지 않는다. 구현까지 이미 허용된 경우 기존 승인 범위에서 이어가고, 새 범위나 필수 미결정만 사용자에게 확인한다.
